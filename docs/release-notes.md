## 这一版改了什么

上一版之后，实际用起来还有两个问题：**项目页很慢**、有时候**连首页都打不开**。
这一版把这两个都查到底、改到位，并且是用真实浏览器冷启动逐条核过页面内容的。

### 1. 项目页慢：找到 128 个「隐形大头」

一个 GitHub 项目页，页面骨架要从 `github.githubassets.com` 下载 **128 个 JS / CSS 文件**。
这些之前全部走直连，同一批 8 个同时下要 **21.3 秒**（单条最长就是 21 秒）。
128 个挤在浏览器的连接槽里，页面自然卡住。

- 现在把这批文件也交给狐径走本地代理：同一批实测 **10.54 秒**，快一倍；
- 顺手把头像、README 配图退回直连（27 KB 头像直连 0.73 秒 ≈ 走代理 0.74 秒，
  直连不慢，就不占建连名额，名额留给主站和这批骨架文件）。

实测同一个项目页（真实浏览器冷启动）：**原版 42.73 秒 → 本版 27.43 秒首次、8.19 秒再次**。

### 2. 打不开：解析出来的地址是假的

本机实测，系统解析 `github.com` 得到的地址是运营商侧的地址段（不是 GitHub 的真实地址），
连上去必然零字节。日志里那些「搬了 0 字节就停」「候选 IP 全军覆没」都是这个原因。

- 现在不采信「解析给谁就连谁」，一律在候选池里按**真下载实测**挑能跑通的地址；
- 同一时刻逐个实测候选地址，只有 `140.82.112.3` / `140.82.113.3` 能返回完整页面（约 1 秒，
  200 OK）；其余 20.x / 4.x / 172.182.x 全部 6~8 秒超时 —— 这类地址会被排到后面，不再优先押注。

### 3. 并发建连的名额调对了

浏览器开一个页面会同时发起五六条连接，之前限制得偏紧（3 条），首页上百个请求时大量排队、
等到超时就主动放弃，页面反而残缺。这一版把上限提到 **6 条**（和浏览器同域并发一致），
排队等待从 6 秒放宽到 10 秒。

实测首页（真实浏览器冷启动）：**首次 13.76 秒、再次 8.21 秒**，且每次都核对页面里
Explore / Sign in / Trending 是否齐全，不是只看大小。

## 已知边界（说明白比藏着重要）

- **第一次打开项目页仍要下 128 个文件**，二三十秒属正常；第二次起走浏览器缓存会到 8 秒级。
- README 里的第三方徽章（shields.io）不经过狐径：本项目只代理 GitHub 自己的域名，
  不转发其他站点的流量。这类徽章本身慢，会占浏览器的连接槽，属客观限制。
- 线路本身质量会波动：同一台机器，故障时段「候选池反复全灭」，连未改动的旧版也打不开。
  本版能做到的是**不押坏地址、快速换边、把并发调对**，不能让线路本身变好。
- 只代理 GitHub 相关域名；**不改 hosts、不改系统 DNS**，退出时还原系统设置。
- 控制面板只监听 `127.0.0.1`，接口已做 Host/Origin 同源校验；危险动作只接 POST。

## 校验与升级

- 升级源仍以 **GitCode** 为主（国内快），GitHub 兜底；
- Ed25519 公钥验签不变：**验不过 / 缺签名 / 签名格式不对，一律拒绝并保留当前版本**；
- 签名私钥只在维护者机器上，绝不进程序、绝不进仓库。
